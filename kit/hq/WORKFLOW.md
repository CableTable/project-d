# Rook HQ: how a session runs (all projects)

Source: `kit/hq/WORKFLOW.md` in the Project D repo, copied to `E:/Project B/Claude/rook-hq/WORKFLOW.md` by `node tools/rook.mjs hq-install` (TODO 219d). After the install Rook edits the HQ copy with Read + Edit like a brief; a code change to the install goes to King in `kit/hq/`.
This file holds what is true for every project. A project's own values are keys of its `rook.config.json` (`name`, `slug`, `extras`, `main`, `support`, `github`, `test`, `browserTest`, `docs.todo|decisions|history|glossary|workflow`, `folders.bishop|king|knight`) and the registry `hq.json` (`projects`, `runs`, `hq`, `runsFrom`); its own rules are in **the project's CLAUDE.md** and its own `docs.workflow` file. Any `node tools/rook.mjs <verb>` takes `--project <D|R|B|P|WF>` (default D). Where the project's file and this one disagree, the project's wins.
Names: **Rook** = the lead (Opus, main account, `claude`), **Bishop** = account 2 (`claude2`), **King** = account 3 (`claude3`), **Knight** = Codex CLI, **Pawn** = Antigravity (`agy`).
One Rook for all projects, one usage budget, one global session number `runs<N>` (from session 41 in `hq.hq`, before in `hq.runs`). Per touched project: one `claude/session<N>` branch and PR.

## Who does what

| Role | Runs on | Does |
|---|---|---|
| Lead (**Rook**) | main account | Plans, picks items, grills, writes briefs, reads short reports (never whole diffs, logs or files), cherry-picks, merges. Writes no code: new behaviour and review findings, however small, go to a builder. |
| Builder (**Knight**) | Codex, builder profile | Builds new items; commits, never pushes; Rook pushes. Never reviews. A ticket touching `kit/base-check*` goes to King (Knight's sandbox skips that test). |
| Builder (**King**) | `claude3`, Sonnet high | Builds when Knight is above 85% of its 5h limit or at 100% weekly; takes every small fix round; leads in Castle mode. Same CLAUDE.md, plugins and memory folder as Rook. Folders: `folders.king.build`, `folders.king.review`. |
| Reviewer | `claude2` (King when Bishop's folder is locked), Opus medium | Reviews every build's commits, read-only, in its own throwaway worktree (`folders.bishop.review`). |
| Other **Bishop** jobs | `claude2` | Mock-ups and screenshots (Sonnet), lookups (Haiku), retros, the project's tester and Bishop-support. Bishop never builds, merges or force-pushes. |
| Research | Knight (gpt-6-luna, read-only) / Pawn | Web research: big -> Knight, quick -> Pawn (https only, no commands, 3 pages, cite). Never run in a repo, never with `--dangerously-skip-permissions` (Knight: never `--dangerously-bypass-approvals-and-sandbox`). |
| Fallback | `claude2`, Opus high | Only when Sonnet has failed at a build. |

Rook's own account runs builder / reviewer Agent subagents too (since 2026-11-04) only below 80% of its 5h limit, in a worktree (`isolation: worktree`; reviewer: `reviewer.md` step 1 does the checkout; builder: `git checkout -b fix/<x> <sha>` first); no queue line.
**Lookups** (his OK 2026-10-24): broad surveys across many files go to a Haiku run on `claude2`, reply in a few lines; small lookups (one grep, one file section, one web page) Rook does itself.
**Knight builds** (his call 2026-10-26): every build goes to Knight; a small fix round goes to King (S29 retro: Knight fix ~18 min, King ~2.5 min); King builds when Knight is above 85% of its 5h limit, at 100% weekly, or he says to run it on Bishop. Knight busy (1 run at a time) is not a reason: the build waits in the queue.
**King's usage:** King week over 70%: merge-critical work first. Review waiting and King and Knight at limit: a `reviewer` subagent, under today's Rook cap. Two `claude2` sessions run at once only on separate files (a mock-up while a build runs).
**Usage numbers** (headless `/usage` does not work): `echo "Reply OK" | <claude|claude2>.cmd -p --model claude-haiku-5-5 --output-format stream-json --verbose | grep -m1 rate_limit_event`; `unifiedWindows.five_hour.utilization` / `seven_day.utilization` (0-1) and their `resetsAt` (Unix time, convert to IST); the same line with `claude` is Rook's account; report both. Check before big work and after each run. No usage report after a merge: the band and the usage page show it.
**Bishop's daily budget:** at most 14% of its weekly limit a day (its week resets Monday 15:30 IST; by the end of IST day k from the reset date as day 1, at most 14% x k; unused budget carries over); a run that would cross today's cap waits; above it only with his OK each time. Above ~0.85 of the 5h window start no new Opus run; let running builders finish (a builder cut off mid-work leaves uncommitted changes: resume it after the reset).

## The loop for one item

1. **Pick** the next open item in `docs.todo` (or what he names). Bugs first.
2. **Grill** (always, every size): the Skill tool for `grilling` AND `domain-modeling` (Rook's first action of every session, both together); rounds of numbered questions each with Rook's recommended answer, `---` between them, written to `runs<N>/grill-<item>.md`. Facts first: finish every lookup, then ask ONE round, never replace one. Full control: Rook takes its recommended answers and goes on; he is told only of major changes (a big behaviour or UI change, a decision reversed, something lost, a merge to main, a blocker). Every "reuse X" answer names the file:function Rook grepped, else "unverified". Terms go to `docs.glossary`, decisions to `docs.decisions`. Bishop-support grills before adding a ticket. `grill-me` / `grill-with-docs` are user-only commands, so Rook calls the two skills they wrap. A tool or app behaviour the project copies from another program (AutoCAD for D) is checked against that program's own help first; where ours differs, say which way is better and why.
3. **Fresh read** (an M / L item, or one resting on an invariant "X never Y"): `node tools/rook.mjs fresh <id> --as king` on the grill file, right after `grill-<id>.md` and before the decisions row and the brief -> `fresh-<id>.out` (max 8 lines; per invariant the code line that keeps it, or "not found"); each line is folded into the brief or the grill, `fresh <n> -> Q<x> | brief line <y> | not needed: <why>`. `--fix` / `--tool` are exempt; `--no-fresh` only for an S item with no invariant. A command shared by two tickets: the grill lists each caller's input (path or bytes) and the return encoding.
4. **Build:** a fresh builder session with a brief (below); keep its `session_id`. `node tools/rook.mjs build ...` (King / Bishop) or `knight ...`.
5. **Review:** `--review` on the launch chains it (when the build ends it launches `review <branch tip>` itself, or writes `NO REVIEW: <why>` into the review out file when the branch got no commit or the build ended in error; `wait` on that file only, it wakes either way); default for King and Knight builds: `--review <runs>/rv-<id>.txt <runs>/review-<id>.jsonl`, the review brief written before launch and naming "the branch tip". Sized: S = spec + bugs (Opus medium), M = + code standards (`ponytail:ponytail-review`, Sonnet high), L or security-touching (keys, rules, file access, credentials) = both on Opus; two reviews are separate fresh sessions in parallel, each in its own folder. A whole-codebase pass is `ponytail:ponytail-audit`. A reviewer reports verified findings only, "severity · file:line · problem · fix", then "ship as is" or "fix first" (which needs a Medium or High). Findings go back to a fresh builder.
6. **Fix:** a short brief (findings + commit range), a fresh session, never `--resume` (a cut-off run only: each resume re-sends the whole conversation). Fix rounds go to King, or Knight when King's 5h is high or its build worktree is busy. A fix that fixes a High, resolves conflicts or is partly done gets a re-review before the suite; its subject ends "(High)", Rook writes `runs<N>/rereview-<sha7>.txt`. A 2nd fix round that finds a new caller / class stops the chain: re-grill the root cause (`runs<N>/grill-<id>-regrill.md`, exactly that name) before round 3. A re-grill names the class the findings share and one rule that closes it (a closed list of forms, everything else unchanged and listed); one Q per finding is not a re-grill (S39: 109a). A finding in the same function as the last round's: re-grill now. More than 2 failed rounds (his rule 2026-11-07): Opus high on King (raw launch with `--model claude-opus-5-5 --effort high` and a hand-written queue line), a Rook `builder` Agent only when King is at its limit.
   **Lows:** ship as is with only Lows: one fix round, no re-review, for Lows he could see or a test that proves nothing; the rest go to `runs<N>/lows.txt` (Rook appends held Lows on reading the review; at session end each becomes a TODO row or "dropped: <why>"). Rook overruling a "fix first" says "overruled fix first: <why>" in its reply and the lows file; an unproven check goes in the lows file (S35 retro).
7. **Cherry-pick** the builder's commits onto the session branch (no pick while a suite runs, no commit in the shared checkout while queue.txt shows one running; before launching the suite read queue.txt and pick every ended review that says ship), tick the row in `docs.todo` (every row of the ticket), commit, push once per handover. Write "ticked" only after that commit and quote its subject from `git log -1`. A UI item: run `board` now, or write "Board due: <id>" in the resume.
8. **Ship:** `node tools/rook.mjs suite <sha>` (`<sha>` must be HEAD; detached, ~20 min, its log `runs<N>/suite-<sha>.log` ends `SUITE unit=<code> browser=<code>`), `wait` on that log; one PR per session number, merged once, on a green run for the head commit. The PR body is in the `pr` skill's shape: a summary visual (file tree / call tree / diff), before / after evidence (tests, screenshots) and a merge-danger call (one-way or two-way door, plus blast radius).

**One check per real failure** (his call 2026-10-20, from the AI-coding forums research): when a worker breaks a rule or a tool fails silently, the fix round also adds ONE small check for exactly that case (a hook, a script line or a test) and the project's history doc names it. No big hook collections. A tool or PATH failure seen twice is a `--tool` ticket now, never a resume note.

Tickets: every M / L item is split into vertical slices one fresh run finishes under 150k context (`result` prints the peak; a run whose peak passes 150k means the ticket was too big: split the rest further); a ticket is one tool family or one command, plus its save / reopen, and a brief listing more than ~5 behaviours is two tickets (S26 retro: every King build peaked 171k-216k); a ticket names what it depends on. Tool tickets (`--tool`) are not counted as items. A tool ticket names at most 10 files (a bigger one is split: S39 219a, 170k). Open tool tickets share no file. A tool brief that adds a refusal says how many recent briefs it would refuse. A move of files out of a repo: the grill asks first "who edits them after the move"; Rook makes no trial moves by hand (S39e: 3 copy-out tries + 219cfix, then deferred).
Split tickets (S38 King retro): before launch the grill lists every way in from the spec with what it passes the other ticket (path, bytes, return type); a way in with no input available becomes a command in the first ticket.
A function gaining a failure result (a throw, a refusal, a false): the grill lists every caller (`grep -n "<fn>("`, hit list in the brief) and what each does on failure; the first build adds a guard test over all of them (S33: 184 took 6 rounds).
A finding that names a class of edits: the first fix brief carries the audit: every site from the class's grep, each mapped or with a quoted reason it is not (S36: 97a). A brief asking for "every X" carries the grep Rook ran with its hit list, and the builder's report quotes the same grep (S31: 175 took 2 fix rounds on "+" buttons a hand list missed).
A brief built from a retro item copies that item's worked value into the Do line and the unit test (S39: 207b built the 84% that retro38l item 1 had called wrong).
Briefs name the base by commit ("from <sha>, contains <sha>"), never by what is on a remote; after a cherry-pick the base is the picked sha. Every build branches from the CURRENT session head, so two builds never conflict on the cherry-pick (S28b: 156b4 from an old base conflicted with 156c).
Pure-geometry style briefs name the case grid and ask for ONE table-driven test over it; where the project has such rules they are in its workflow file.

## Commands (Git Bash, from the project's repo folder)

### Rook card
- A state claim to him (fixed, ticked, flaky, who ran it, why I hand over) names its proof in the same line: output line, sha or file:line; none in hand: "unchecked". A run report names the account.
- Usage gate (before every launch): `node tools/rook.mjs usage --cached`; pick the worker with headroom, wait for a reset or pause. Rook's own week: 14% x k by the end of IST day k from the Sunday 15:30 reset; at the cap finish the step, say so in one line, pause till the next day. Bishop 14% a day (20% in Castle mode).
- Launch: `node tools/rook.mjs build <brief> <out.jsonl> <branch> <sha> [--as king|bishop] [--no-fresh] [--fix] [--regrilled] [--tool] [--over] [--big] [--review <review brief> <review out.jsonl>]`, `node tools/rook.mjs knight <brief> <report.txt> <branch> <sha> [same flags]`, `node tools/rook.mjs review <sha> <brief> <out.jsonl> [--as king|bishop] [--from <clone> <branch>]`. Branch always new: `king/<id>`, `king/<id>fix`, never `claude/session<N>`. The launch refuses: an existing branch, a path not written `../runs<N>/`, over 5 numbered Do lines, a bare runs path, a handover-due count (below), a missing grill / fresh file, a re-grill file not named exactly `runs<N>/grill-<id>-regrill.md`. `<branch>` is the same in the brief's Branch line (`king/<id>` build, `king/<id>fix` fix round from the build's head).
- Brief lint (build / knight, `--fix` too): refuses more than 5 numbered non-routine behaviour lines, one-word browser filter pieces, a full-suite request unless the line names Rook or directly negates it, a bare `runs<N>/` path, a line starting `Also`, a `Tick` line naming two ids; `--big` overrides. Every launch (build / knight / review, `--fix` too) writes `<kind> <branch|sha> -> <out file>: running` into `runs<N>/queue.txt` (lines 1-2 stay) and the run's end rewrites it to `ended`; the launch empties an existing report file, so `wait` waits for the new report; a Knight run's log is the report's name with `.log`; `knight` fetches unpushed local commits into its clone itself (never undo a commit for Knight: to drop one anyway `git reset --soft HEAD~1`).
- Handover gate (TODO 165): the 3rd NEW-item launch per Rook is refused ("handover due"); state is in `runs<N>/rook-gate.json` and line 2 of queue.txt (`gate` rewrites it, `, <k> tool` is added for tool tickets). `--fix` marks a fix round (allowed up to the 2nd round of an item; the 3rd needs `--regrilled` after a re-grill); a brief whose line 1 starts `King fix`, `Knight fix` or `Fix round` counts as one without it; `--tool` passes the gate and is not counted; `--over` lets a 3rd item through (his OK only). A new Rook rewrites rook-next.txt (new uuid) at its start, which resets the count; until its `claude/session<N+1>` branch exists locally, item launches are refused (fix / `--over` pass). Every launch is refused with `HANDOVER: context <N>k` once this Rook's context passes 150k (`--over` passes).
- Review by hand: without `--as` it goes to Bishop, or King when Bishop's reviewer folder is locked (prints `review: Bishop busy, King`; both locked is refused; Bishop paused: `--as king`); `--from <clone folder> <branch>` = a Knight build's clone (also runs `npm.cmd ci` there). Rook never reviews inside its own session; when he asks for a Rook review it offers King first in one line. A Knight branch is fetched into the repo first, or its sha is unknown there (S28 lost a launch). A branch for a build is made with `switch -c <branch> <sha>`, always a commit id, never FETCH_HEAD (it is per worktree and goes stale: S26 retro); King's worktree shares the repo's objects, so it needs no fetch. After the build Rook pushes.
- Lookup of this card: `sed -n '/^### Rook card/,/^Briefs start/p' <hq>/WORKFLOW.md`.
- Run ended: `node tools/rook.mjs result <run file>` (report, denials, peak context), on the done file only. `node tools/rook.mjs fails <log>` for a red log. `node tools/rook.mjs gate` rewrites queue.txt line 2.
- Wait: `node tools/rook.mjs wait <run file>... [--ci <sha>]` as a Monitor (ToolSearch `select:Monitor,TaskStop` first), never in the foreground; arm it, then end the turn (no placeholder commands). `wait` prints `DONE <file>` when the first run ends or `CI RUN <id> <conclusion>`; with run files `CI RUN none <reason>` (no CI run found, e.g. a branch with no PR) is only printed and the wait goes on, while `--ci` alone exits 1 there. Run `wait` as a Monitor, never in the foreground (it prints only at the end: S33f). Jobs that must run one after another go in ONE background script, plainly in order, never a second script waiting for the first one's file; write each script fresh, never by `sed` on another script, and print it (`head`) before launching it; any wait loop has a time limit and prints what it waits for; check within ~2 min of a run's planned start that its output file exists (a background run uses `--output-format stream-json --verbose`; a missing output file is a bug, not progress). When a builder frees up, launch the next item whose files do not overlap the running build in that same turn.
- CI of a push: Monitor `bash tools/ci-watch.sh <sha>` on the head sha only (CI runs the head; an older sha of the same push has no run), one per push, Monitor `timeout_ms` 30 min (Bash and PowerShell take `timeout`), re-arm on expiry or `bash tools/ci-watch.sh --run <id>`; a release run on main passes 30 min. It prints each finished job and ends with `RUN <id> success|failure`. Never pipe to `jq` (not installed: a silent watch); use gh's own `--jq`. Push again only after the `RUN` line (a `build: success` line is one job; a new push cancels the running tests: S28). Every wake-up costs a re-read of the conversation: say nothing on a job that passed. A CI red step added in this PR is a bug (write the fix brief now); a flake only for a step older than the PR (S39e: 210, 24 min). `gh ... --jq` runs in Bash only. Repo for gh: `node tools/rook.mjs repo`.
- Board / look: `node tools/rook.mjs board <brief> <out>`. Pawn: `node tools/rook.mjs pawn <out.json> "<one question>"`. Acad (the project's own app checks): `node tools/rook.mjs acad <item>`.
- Retro: `node tools/rook.mjs retro` when the session's last item is cherry-picked (by 01:00 IST: Bishop needs 5h room; `--as king` when Bishop is short); at a handover `node tools/rook.mjs retro --handover` first. Read each `retro<N>*.out` whole, once, before any edit; apply what it recommends; write `retro<N>.applied`.
- 05:00 merge (`merge --due`) needs: CI green on the head, `retro<N>.out` not empty, `retro<N>.applied`, `merge-ok-until.txt` >= today. By hand: `node tools/rook.mjs merge <n> <sha>`.
- A turn ends with a waiter running or a question for him; a clear next step with nothing running is done in the same turn. While runs go, no status messages. Run ended, no major change: no text to him; the state is in queue.txt. Your own recommended answer: take it and note it. Asked him and you hold a pick: take it now, write it in the grill file, tell him once ("took X; say if not"). A resume says "waits for his answer" only for what only he knows (a credential; a file name only after listing recent files of that type and asking "which of these"); that question goes in one message per Rook. A turn also ends only once a waiter for a run still going has started (S29: builds sat done 4.7 h while Rook said "still building"); a clear next step with nothing running, status questions included, is done in the same turn (S33c: 6 h idle).
- Waiting on a reset: do grills and briefs first and launch whatever has headroom, start the timer last (a gap over 60 min re-caches the whole context: S39 49k).
- One call per step, short output: `node tools/rook.mjs usage` (3 lines) and `node tools/rook.mjs result <run file>` (the reply + tokens); write the brief with the real base sha already in it, then launch with one plain `build|knight|review` call (S31: two `sed -i` + launch chains denied). Run reports to him are in tokens: total = input + cache read + cache write + output from the final `result.usage`, new = input + cache write + output (Knight: the "tokens used" line in its run.log); the `--max-budget-usd` caps stay as a safety stop. A run can be watched or taken over: `claude2 --resume <session_id>`; print only `result`, `session_id`, `usage` and `permission_denials` of a run's JSON.
- Rook runs the full browser suite once per push, in the background, on the combined head, only after every review on the branch says ship (S31b ran it twice); commits after a green suite that touch only docs or a unit test rerun the unit tests only, and the report gives suite results per sha when unit and browser differ (S35). Rook tries a `.claude/` edit once itself and writes `runs<N>/paste-*.txt` for him only after a denial; it never reads skill or reference docs it has read before in the session; a plan for him stops at this PR's merge (later items under "session <N+1>").
- Change any file (brief, queue.txt, a doc) with Read + Edit (`replace_all` for a rename) in the same turn (launchers rewrite queue line 2), never `sed -i` or a heredoc, never a chain with a launch (denied, S30 retro); git and launches go in their own command. Briefs go to a file with the Write tool and in on stdin.

Briefs start from `kit/briefs/<kind>.txt` (build, fix, review, retro, board).

### Every brief says
- **Report shape** (max N lines): Result (done / not done, commit id), Tests (what ran, pass / fail), Findings (or "none"), Not checked.
- "You ARE the builder / reviewer: do the work yourself, never launch claude2 or Agent subagents." (Without it a `claude2` run reads CLAUDE.md's builder rule and tries to start `claude2` itself.) Builders use ponytail full (his call 2026-10-21); plain commands, no `cd ... &&`, no `$?` tricks; a refused command is reported, not worked around. The worktree is already the working folder: no `cd "<worktree>" &&` prefix (denied 6-11x a run). A builder outside the main folder needs `--add-dir` for the git dir and `git add` / `git commit` in its allowed tools; a run whose first commit is refused stops and reports. "Commit on the branch, never push" and the commit trailer live in `AGENTS.md`, `.claude/agents/builder.md` and `reviewer.md` (the project's copies), so briefs from `kit/briefs/` do not repeat them; screenshots go to Bishop-look.
- Branch name (new), spec file, files it may touch, what not to stage, the base by commit ("from <sha>, contains <sha>"; never what is on a remote; after a cherry-pick the picked sha), paths into runs as `../runs<N>/`, `Tick`: TODO.md left alone (Rook ticks after the cherry-pick), commit on the branch, never push.
- Git verbs the builder may use: `add`, `commit`, `fetch`, `checkout`, `switch`, `cherry-pick`, `rebase`, `apply`; squash = `cherry-pick -n`.
- Tests: the project's `test` and the item's own new or changed steps; never the full suite (Rook runs it once per push on the combined head, in the background, after every review says ship). Reviewers run the project's `test` and the steps `reviewer.md` step 3 names, never the full suite (his call 2026-10-28, after builders' filtered runs missed 2 old steps and CI went red).
- **Proof before "done":** a report claims only what a command run AFTER the last edit showed; each claim quotes that line; anything not run goes under Not checked. A tool that starts a process, task or window: one real start on a harmless target (a notepad .lnk from a `tmp-*.mjs`), quoted; fakes don't count (S35: `next` passed its injected-spawn tests and started nothing); no quoted start = a Medium in review. Reviewers check the quotes against the commit. No "should work" / "looks right" without a quoted run.
- **Fix briefs** name their source (a review finding number); anything else is marked *Rook's idea*, with the behaviour that must still work; each finding names its case grid and the fix adds ONE table-driven test over it. A new check (lint, guard, regex) is run over the real files first; the brief names must-refuse and must-pass lines from them. A function gaining a failure result: the brief lists every caller (`grep -n "<fn>("`). A brief asking for "every X" carries the grep Rook ran and its hit list. A base older than HEAD where HEAD added a lint: the brief quotes the rule. A reason naming other code gives its file, or says it is not built yet. The review brief copies the fix brief's rule line word for word and takes its base sha from the fix brief (S32 retro). A new check (lint, guard, regex) has a corpus (S32 retro: 172 and 180 took 3 rounds each): Rook runs it over the real files before the brief, the grill lists the hits, and the report quotes the must-refuse and must-pass lists from a run over the corpus.
- A bug or flake brief: the builder runs `mattpocock-skills:diagnosing-bugs` first and reproduces; the report says "reproduced" or "not reproduced: likely cause" (a CI-only failure: the downloaded artifact, Linux timing, CPU throttling). Knight gets the same loop as a line pointing at that skill's SKILL.md.
- Reviewers use `ponytail:ponytail-review` for a build's commits (verified findings only), `ponytail:ponytail-audit` for a whole-codebase pass; review briefs start from `kit/briefs/review.txt`. Review A checks the "Done when" list, including the quoted FAIL on the base.
- Done when: the decision row, new words in the glossary, the tests, one commit; a new test prints FAIL on the base under `node tools/base-check.mjs <base-sha> <test-file>`, and the report quotes that FAIL (S30 retro).
- Time limits: any run stops and reports at 60 min; a WIP commit of untested code says so in the report's first line. A cut-off run: builders WIP-commit each passing slice; after the reset a FRESH run with the brief plus "STATE: a previous run left uncommitted work; read git status and the diff, finish, test, commit" (Knight: never `exec resume`, it takes no `-p` / `-C` / `--add-dir` and cannot commit in a clone). A build that stopped on a question or a red it cannot settle commits one `WIP TODO <id>: <why>` itself (hooks on) and says so in the report's first line; its fix round starts from that sha. Each passing slice of a long build is WIP-committed as it goes (a limit cut gives no last turn).
- Reports to him are in tokens (total and new), never dollars; limits in %.

## Handover and session end

- **Handover** at a clean break once ANY of: 2 items built and reviewed since this Rook started (fixes and tool tickets don't count; the launcher enforces it: the 3rd new item is refused, `--over` with his OK), context ~150k (auto-compact ~218k; limit 250k), he is shutting down, a usage reset is near. A merge alone is no reason.
